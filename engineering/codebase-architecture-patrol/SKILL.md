# Codebase Architecture Patrol

对仓库做一次只读的架构巡检，产出「深化机会」报告：把 shallow module（接口复杂度接近实现）变成 deep module（小接口背后藏大量行为）的候选。你只报告，不动手。

## 巡检纪律

### 1. 先读仓库现状文档

读 `AGENTS.md` / `CLAUDE.md` / `CONTEXT.md` / `docs/adr/`（有哪些读哪些）。其中已记录的决策不再重新建议；与 ADR 冲突的候选，只有摩擦足够真实才报，并标注「与 XX 冲突，因为…」。

### 2. 圈定范围：只看上周合入 main 的提交

按今天日期算出上周一 00:00 与本周一 00:00（本地时区），然后：

```bash
git log --first-parent main --since='<上周一 00:00>' --until='<本周一 00:00>' --oneline --name-only
```

- 热点文件只从这批提交触碰的文件里选，优先扫其中改动最活跃的路径。
- 范围外（更早的存量代码）不主动扫；只有上周改动直接暴露存量问题时，在报告里作背景带一句，不单独立候选。
- 上周 main 无提交：如实报告本周无发现，收工。

### 3. 只找深化机会

摩擦信号：理解一个概念要在多个小模块间跳 / 接口和实现一样复杂 / 纯函数只为可测试性抽出而真 bug 在调用方 / 紧耦合模块越过 seam 互相泄漏 / 无测试或必须绕过现有接口才能测。

**每个候选必须过 deletion test**：删掉该模块，复杂度是「集中」还是「转移」？只有「集中」的入围。

顺带发现的 correctness bug 不是深化机会——只有它暴露了 shallow 结构时才作为该候选的佐证出现，否则不报。

### 4. 方案按依赖分类，分类决定测试方式

1. 纯进程内（无 I/O）：合并模块，在新接口上直接测，不需要 adapter。
2. 本地可替换（嵌入式 PG、内存文件系统等测试替身）：用替身在测试套件里测；seam 留在模块内部，不外暴露到接口上。
3. 远程但自有（自家服务跨网络）：在 seam 处定义 port，逻辑收进一个 deep module，生产挂 HTTP/队列 adapter、测试挂内存 adapter。
4. 真外部三方：外部依赖注入为 port，测试给 mock adapter。

**seam 纪律**：一个 adapter 是假想 seam，两个才是真 seam。建议引入 port 必须说清第二个 adapter 是谁（通常是生产 + 测试），说不清的就是纯间接层，降为 Speculative 或淘汰。

测试写在新模块的接口上（接口即测试面），断言可观察行为而非内部状态；旧浅模块的单测在接口测试落地后删除——替换，不叠加。

## 前端同等入围

shallow 信号按前端形态识别：透传 props 的包装组件、只包一层 fetch/转调的 hook、与实现一样宽的组件 API、为绕开重渲染抽出的纯展示壳（真逻辑仍在调用方）。

边界违规与深化机会同等报告，但规则以仓库自身声明为准（AGENTS.md / CLAUDE.md / 架构文档里写明的分层与依赖方向），仓库没声明的不臆造。检查点：

1. 依赖方向：UI 组件引了业务/数据层、底层反被上层回调注入。
2. 状态归属：服务端状态（请求缓存）与客户端状态（表单、筛选、草稿）混放；把服务器数据整份镜像进客户端 store 是重点信号。
3. 层职责：通用 UI 组件混入业务逻辑或数据获取；业务组件直接操作平台 API。

判定仍走 deletion test 和依赖四分类，不因是前端放松标准。

## 报告规范

报告写成一个 markdown 文件，落在仓库外：用户指定了路径就写到指定路径，否则写到系统临时目录 `<tmpdir>/architecture-patrol-<日期>.md`。仓库内不留任何文件。

每个候选一张卡片，字段顺序固定：

1. **文件**：涉及的文件/模块
2. **问题**：当前架构造成的摩擦
3. **方案**：改什么，含依赖分类和测试策略
4. **收益**：用 locality（理解与改动集中一处）和 leverage（一处深化多处受益）解释，说明测试如何改善
5. **推荐强度**：`Strong` / `Worth exploring` / `Speculative`

结尾给 **Top recommendation**：最先做哪个，为什么。

命名用仓库业务词汇（以 AGENTS.md/CONTEXT.md 词汇表为准，如「订单」「入库单」），禁止「重构 XxxHandler/Service」这类空话。

仓库缺失 AGENTS.md / CONTEXT.md / docs/adr 时，报一条 Speculative 元候选：决策无记录、词汇无共识、边界规则无法声明。

如实分级、宁缺毋滥：没有值得报的就明确写本周无发现。

## 越界即停

遇到「顺手修一下」「直接改文档」的诱惑，停——把建议写进报告，行动留给人。你不提交、不开 MR、不改仓库里的任何文件。

## 红旗——出现即停下重读纪律

| 诱惑 | 现实 |
|---|---|
| 「扫全仓库才彻底」 | 范围纪律就是防回归成全库扫描；上周窗口外的存量问题不立候选，最多作背景一句 |
| 「这个 bug 太明显必须报」 | bug 不是深化机会；只在它暴露 shallow 结构时报 |
| 「报告太空不好看」 | 没有发现就写无发现；硬凑的报告消耗的是信任 |
| 「仓库没写规则，我按最佳实践提」 | 没声明的规则不臆造；文档缺失走 Speculative 元候选 |
| 「顺手把这个改了」 | 只读纪律；建议进报告，行动留给人 |

## 思想来源

深化机会的分析框架（shallow/deep module、deletion test、seam 纪律、依赖四分类）参考自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `codebase-design` 与 `improve-codebase-architecture`，后者又源自 John Ousterhout《A Philosophy of Software Design》。本技能是定期巡检形态：无 grilling loop 与 HTML 报告，范围收窄为上周合入 main 的提交。原版 MIT 许可。
